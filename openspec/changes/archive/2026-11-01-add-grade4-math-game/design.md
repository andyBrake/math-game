# Design

## Context

仓库此前为空（无任何提交），本设计从零建立结构，因此没有既有代码约定需要兼容。约束来自 proposal 与 specs：纯本地、零第三方依赖、`file://` 下可直接打开、无构建步骤、界面中文。

关键约束的由来：

- **禁止 ES Module 与 `fetch`**：`file://` 协议下浏览器把每个文件视为不透明来源，模块脚本和 XMLHttpRequest 都会被 CORS 拒绝。这直接决定了脚本引入方式和数据文件的形态。
- **`localStorage` 在 `file://` 下不可靠**：Chrome 允许但作用域是整个 `file://`，Safari 与部分隐私模式直接抛异常。因此存储必须可降级。
- **教材内容是数据不是代码**：17 个单元、约 50 个知识点，若把题目逻辑与单元信息混写，后续增补年级会牵一发动全身。

## Goals / Non-Goals

**Goals:**

- 单页、多文件、经典脚本组织，双击 `index.html` 即可游玩。
- 教材数据、题目生成、渲染、战斗状态机四层解耦，新增单元只改数据与生成器。
- 同一套战斗状态机同时服务单元关（6 题、有血量）与学期测验（20 题、无血量）。
- 视觉素材全部可由代码生成，图片仅作为可选覆盖。
- 所有路径与资源引用都相对于仓库根目录，文档、代码与配置中不出现绝对路径。

**Non-Goals:**

- 不做账号、云同步、排行榜等任何联网能力。
- 不做题目编辑后台或家长自定义题库。
- 不为一年级至三年级、五年级至六年级实现内容，只保留数据结构占位。
- 不做移动端竖屏适配与打包成桌面应用的方案，先保证浏览器可玩。

## Decisions

### D1：多文件 + 经典 `<script>` + 全局命名空间

用 `<script src="...">` 顺序加载，每个文件挂到单一全局对象 `window.MG` 下（`MG.data`、`MG.gen`、`MG.battle` 等）。数据文件写成 `MG.data.curriculum = {...}` 的 JS 字面量而不是 JSON，避免 `fetch`。

*替代方案*：单文件内联全部内容（双击体验最好，但 3000+ 行难以维护、diff 噪音大）；ES Module + 本地服务器（结构清晰，但破坏"双击即玩"）。

### D2：教材数据与生成器分离，用 id 关联

`data/curriculum.js` 只描述结构：

```
grade -> semester -> unit { id, name, order, topics: [{ id, name, gen }], hasGraphics }
```

`data/generators/` 按知识点注册 `MG.gen.register(id, fn)`，`fn(level)` 返回题目对象。curriculum 只引用 `gen` 字符串 id，不引用函数本身，因此两侧可独立演进，缺失引用由启动自检报错。

*替代方案*：单元对象直接内联生成函数（少一层间接，但数据文件会变成巨型代码文件，且无法被自检校验完整性）。

### D3：题目协议统一为纯数据

```
{
  topicId, level,
  renderer: "text" | "canvas",
  prompt,                 // 题干文本
  canvas: { kind, ... },  // renderer 为 canvas 时的绘制数据
  options: [4 项],
  answerIndex,
  explain
}
```

渲染层只认这个结构，不认知识点。`canvas.kind` 决定调用哪个绘制函数（`bar-chart` / `angle` / `symmetry` / `blocks`），新增图形类型等于新增一个绘制函数。

*替代方案*：生成器直接返回 HTML 或 canvas 指令（灵活但把表现逻辑泄漏进内容层，且难以自检）。

### D4：一个状态机服务两种模式

`js/session.js` 维护 `{ mode: "level" | "exam", queue, index, hearts, hp, combo, answers[] }`；`mode` 只影响三处：初始参数、答错分支、结算模板。战斗视图与考试视图共用同一套题目渲染与答题卡片。

*替代方案*：两套独立流程（各自简单，但题目卡片、计时、选项按钮会重复实现两遍）。

### D5：难度与题目队列在开局时一次性生成

进入关卡时一次性抽满 6 题（难度 1,1,2,2,3,3）并覆盖该单元全部知识点；答错时只就地替换当前题（同 topicId、不同数字），不重新洗牌。这样"第几题"与难度始终对齐，也让连击与必杀的计算可预期。

*替代方案*：逐题懒生成（实现简单，但无法保证知识点覆盖与难度曲线）。

### D6：像素画用代码绘制到离屏 canvas

角色与敌人用 `16x16` 调色板数组描述，启动时绘制到 `canvas` 并缓存为 `ImageBitmap`/离屏元素，动画靠切换 2~4 帧。`assets/characters/<key>.png` 存在时优先加载图片，加载失败静默回退。

*替代方案*：引入现成像素图集（风格易不统一、需要外部文件、可能破坏离线可玩）；用 CSS `box-shadow` 拼像素（可读性差、性能差）。

### D7：音效用 WebAudio 即时合成，无 BGM

`AudioContext` + 方波/三角波振荡器包络，五种事件各一个短音型。点击静音只置标志位。用户首次交互后才创建 AudioContext，避免自动播放策略拦截。

*替代方案*：内置 wav/mp3 文件（需要素材、体积大、与零依赖目标相悖）。

### D8：存储适配层带内存降级

`js/store.js` 暴露 `load()/save()`，内部 `try { localStorage } catch {}`，失败时切到内存对象并设置 `degraded` 标志，由壳层渲染提示条。存档结构带 `version` 字段，读到时若版本不匹配则迁移或重置，避免旧存档导致白屏。

### D9：图形题在 Canvas 中重绘而非截图

统计图、角、对称轴、等距方块图均由绘制函数按数据重绘。等距方块使用 2:1 菱形投影，正方体集合由生成器给出整数坐标。量角器题改为"给出角度选分类/比较"的选择题，不要求读数。

### D10：路径一律相对仓库根目录

`math-game/` 是代码仓库根，`WorkBuddy/` 是它所在的项目根。文档中的路径、`<script src>` / `<link href>`、图片与数据引用、README 里的命令，全部写成相对仓库根的形式（`js/main.js`、`data/curriculum.js`、`assets/characters/mario.png`）。代码内部不拼接绝对路径，也不依赖 `window.location` 的绝对形式；本地服务启动命令统一写成在仓库根执行的 `python -m http.server`。

*替代方案*：用绝对路径（在本机可跑，但换机器、换目录或提交到别处就会失效，也会把用户名写进文档）。

## Risks / Trade-offs

- **`file://` 下无模块化导致全局命名空间污染** → 所有模块统一挂在 `MG` 下并加 `MG.gen.register` 这类受控入口，禁止裸全局变量；文件加载顺序在 `index.html` 中显式排列并注释。
- **Safari 等浏览器禁用 `localStorage`** → D8 降级 + 界面提示；README 给出 `python -m http.server` 的推荐启动方式（标准库，不算依赖）。
- **自动出题出现"数学上对但教材外"的题**（例如四下用两位数除法出三位数除以三位数）→ 每个生成器显式声明取值范围，自检对知识点跑 1000 题校验；发现越界按知识点报错。
- **干扰项设计不当会让题变简单**（错项差异过大一眼排除）→ 干扰项集合在生成器里显式构造并做数量级校验，尽量与正确项同位数。
- **像素画可辨识度** → 每个角色限制在 16x16 且用高对比配色；若辨识度不足，保留 `assets/` 覆盖路径作为兜底。
- **6 题一关可能覆盖不全一个单元的知识点**（单元有 4 个知识点时必然有取舍）→ 采用"轮转"抽题：每局起点轮换，多次游玩后自然覆盖全部知识点；结算页展示本局覆盖到的知识点。
- **测验组卷按权重可能重复同一知识点** → 组卷时先按单元分桶再在桶内做知识点轮转，同一知识点在 20 题内最多 3 次。

## Migration Plan

全新项目，无需迁移。落地顺序：数据与生成器 → 渲染层 → 会话状态机 → 视图壳 → 存档与报告 → 素材与音效。每完成一层即可在浏览器中验证，不依赖前一层之外的产物。

## Open Questions

- 关卡与测验的具体配色方案与像素字体样式，可在实现阶段边看效果边定，不影响结构。
- 是否需要在报告页加入"按学期导出错题清单"的文本复制功能，属可选增强，不影响本次范围。
